# データベース設計

SQLite に保存するデータの設計です。画面は `docs/screens.md`、ルートは `docs/routes.md`、要件は `docs/requirements.md` にあります。データベースアクセスは Peewee を使います。

写真ファイル本体はデータベースに入れません。アプリ内のフォルダに置き、データベースには保存時に付けたファイル名だけを記録します。データベースファイルと写真のフォルダは、Git の管理対象外です。

コメント、検索、フォロー、キャプション編集は、この初期版のテーブルには含めません。

## テーブル一覧

| テーブル | 役割 | このテーブルが必要な理由 |
| --- | --- | --- |
| `users` | アカウント | 投稿する前に、ログインする人が存在する。名前やパスワードを、投稿のたびに繰り返して保存しない |
| `posts` | 写真1枚の投稿 | 一覧に出す写真、キャプション、投稿者、投稿日時が1行にまとまる。1人が複数投稿できる |
| `likes` | 誰がどの投稿にいいねしたか | いいねの追加と取り消し、1人1回まで、いいね数の表示を、行の追加・削除・件数で扱う |

3つに分けるのは、寿命が違うからです。ユーザーは投稿がなくても登録できます。投稿はユーザーが残します。いいねは、あとから付けたり外したりします。1つの表に混ぜると、投稿がないユーザーを保存できず、同じ人のパスワードを投稿の数だけ複製することになります。

## テーブルの関係

```text
users 1 ──── * posts
users 1 ──── * likes
posts 1 ──── * likes
```

- 1人のユーザーは、複数の投稿を持てる
- 1人のユーザーは、複数の投稿にいいねできる
- 1件の投稿は、複数のユーザーからいいねされる
- 同じユーザーが同じ投稿にいいねできるのは1回まで
- 投稿を削除したら、その投稿へのいいねも一緒に消す

いいね数は `posts` に列を持ちません。一覧を出すときに `likes` の行を数えます。数を別の列にも持つと、いいねの追加・取り消しのたびに両方を更新する必要があり、ずれが起きます。

## users

登録とログインのためのテーブルです。ログインはユーザー名とパスワードで行います。メールアドレスは登録時に受け取り、同じアドレスの再登録を防ぎます。

| カラム | データ型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | INTEGER | 主キー。自動採番 | ユーザーを区別する番号。他のテーブルはこの番号を参照する |
| `username` | TEXT | NOT NULL。ユニーク。大文字小文字を区別しない。最大30文字 | ログインに使う名前。`Alice` と `alice` は同じ名前として登録できない |
| `email` | TEXT | NOT NULL。ユニーク。大文字小文字を区別しない。最大254文字 | 登録時のメールアドレス。`User@example.com` と `user@example.com` は同じアドレスとして登録できない |
| `password_hash` | TEXT | NOT NULL | パスワードをハッシュ化した値。平文のパスワードは保存しない |

主キーは `id` です。

外部キーはありません。

ユニーク制約は次の2つです。

- `username`
- `email`

ユーザー名を30文字、メールアドレスを254文字にするのは、列に際限なく長い文字列を入れないためです。254文字はメールアドレスで一般的に使われる上限です。SQLite は TEXT の長さを強制しないので、超えていないかの確認はアプリ側で行います。

`password_hash` の長さはハッシュの方式で変わります。方式を変えても列を変えなくて済むよう、固定の短い上限は置きません。

## posts

投稿一覧と投稿作成のためのテーブルです。1行が写真1枚です。投稿者はユーザーそのものではなく、`users.id` の番号で指します。

| カラム | データ型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | INTEGER | 主キー。自動採番 | 投稿を区別する番号。削除やいいねの URL に使う |
| `user_id` | INTEGER | NOT NULL。外部キー | 投稿者。`users.id` を参照する |
| `image_filename` | TEXT | NOT NULL。ユニーク。最大255文字 | フォルダへ保存したファイル名。利用者が送った元のファイル名は保存しない |
| `caption` | TEXT | NOT NULL。デフォルトは空文字。最大200文字 | キャプション。空でも投稿できる |
| `created_at` | DATETIME | NOT NULL | 投稿日時。サーバーが保存時に入れる。一覧は新しい順に並べる |

主キーは `id` です。

外部キーは次のとおりです。

| カラム | 参照先 | 投稿者であるユーザーを削除しようとしたとき |
| --- | --- | --- |
| `user_id` | `users.id` | 削除しない。この初期版にユーザー削除はない。投稿が残っているユーザーを、データベース操作で誤って消さないための制約 |

ユニーク制約は `image_filename` です。1件の投稿が1つのファイル名を持ちます。ファイル名が重なると、一方の投稿を削除したときに、もう一方が参照しているファイルまで消す判断が難しくなります。

キャプションの空は、NULL ではなく空文字にします。NULL と空文字の両方が「キャプションなし」を意味すると、表示のときに二通りの扱いが必要になります。200文字を超えていないかの確認はアプリ側で行います。

## likes

いいねの追加、取り消し、件数表示のためのテーブルです。一覧では各投稿のいいね数を出します。ログイン中のユーザーは、同じ投稿に対していいねを付けたり外したりできます。

「誰が」「どの投稿に」の両方が必要なので、投稿テーブルに件数だけを持つ形にはしません。件数だけだと、取り消すときにその人のいいねかどうかが分からず、1人1回の制限もできません。

| カラム | データ型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | INTEGER | 主キー。自動採番 | いいね1件を区別する番号 |
| `user_id` | INTEGER | NOT NULL。外部キー | いいねした人。`users.id` を参照する |
| `post_id` | INTEGER | NOT NULL。外部キー | いいねされた投稿。`posts.id` を参照する |

主キーは `id` です。`user_id` と `post_id` の組み合わせを主キーにすることもできます。この初期版では、各テーブルの主キーを `id` にそろえます。1人1回の規則は、主キーとは別にユニーク制約で守ります。

外部キーは次のとおりです。

| カラム | 参照先 | 参照先を削除したとき |
| --- | --- | --- |
| `user_id` | `users.id` | 削除しない。ユーザー削除機能はない |
| `post_id` | `posts.id` | 一緒に消す。投稿を削除したら、その投稿のいいねも消す |

ユニーク制約は (`user_id`, `post_id`) の組み合わせです。同じ組み合わせの行は1件だけにします。

## インデックス候補

ユニーク制約を付けると、SQLite はその列（または列の組み合わせ）にインデックスを作ります。ログイン時のユーザー名検索や、登録時の重複確認は、このインデックスを使えます。

Peewee の外部キーは、指定を変えない限り、その列にもインデックスを作ります。`posts.user_id`、`likes.user_id`、`likes.post_id` が該当します。

| インデックス | 種別 | 使う処理 | 扱い |
| --- | --- | --- | --- |
| `users.username` | ユニーク | ログイン、ユーザー名の重複確認 | ユニーク制約として付ける |
| `users.email` | ユニーク | メールアドレスの重複確認 | ユニーク制約として付ける |
| `posts.user_id` | 通常 | 投稿者本人だけ削除できるかの確認 | 外部キーに伴って付く |
| `posts.image_filename` | ユニーク | 保存したファイル名の重複確認 | ユニーク制約として付ける |
| `posts.created_at` | 通常 | 投稿一覧を新しい順に並べる | 候補。件数が少ないうちは、並べ替えだけでも足りる |
| `likes` の (`user_id`, `post_id`) | ユニーク | いいね済みかの確認、1人1回の制限 | ユニーク制約として付ける |
| `likes.post_id` | 通常 | 投稿ごとのいいね数、投稿削除時のいいね削除 | 外部キーに伴って付く |

`likes` のユニーク制約は (`user_id`, `post_id`) の順です。このインデックスは「このユーザーのいいね」や「このユーザーがこの投稿にいいねしているか」の検索に使えます。左端が `user_id` なので、「この投稿のいいねを全部数える」検索には向きません。投稿ごとの件数には、`post_id` 単独のインデックスを使います。

そのため `likes.user_id` だけのインデックスは、複合ユニークと役割が重なります。Peewee で外部キーの自動インデックスを残すと両方ができます。実装時は、`likes` のユーザー側の外部キーだけ自動インデックスを外し、複合ユニークに任せます。`likes.post_id` のインデックスは残します。

このアプリの想定は、自分の PC で少人数が使う規模です。インデックスがなくても動作します。上の表は、一覧・ログイン・いいねの切り替えで繰り返し探す列です。

## Peewee で実装する場合の注意点

### フィールド名とカラム名

データベースの列名は `user_id` と `post_id` にします。保存するのは関連する行の `id` だからです。

Peewee では、外部キーのフィールドを `user` のように関連先の名前で定義すると、データベースの列名は自動で `user_id` になります。コード上の `post.user` は投稿者のユーザーを取り、`post.user_id` は番号だけを取ります。モデルのフィールド名を、列名の代わりに設計へ書かないようにします。

### 外部キーを有効にする

SQLite は、接続のたびに外部キー制約を有効にしないと、参照のチェックも、投稿削除に伴ういいねの削除も動きません。Peewee で SQLite へ接続するとき、外部キーを有効にする設定を入れます。

`likes.post_id` には、参照先の投稿が削除されたらいいねも削除する設定を付けます。`posts.user_id` と `likes.user_id` には、参照先のユーザーを削除させない設定を付けます。

データベースの行を消しても、フォルダ内の画像ファイルは残ります。投稿削除の処理では、行の削除とは別に、その投稿のファイルをアプリが削除します。

### 大文字と小文字を区別しない一意制約

SQLite のユニーク制約は、そのままでは大文字と小文字を別の値として扱います。`username` と `email` には、英字の大文字小文字を同一視する照合（`NOCASE`）を付けます。これで `Alice` と `alice` の両方は登録できません。

この照合が同一視するのは、英字の A から Z です。

### 文字数と空のキャプション

`CharField` や `TextField` に最大文字数を書いても、SQLite はその長さで保存を拒否しません。ユーザー名30文字、メールアドレス254文字、キャプション200文字、ファイル名255文字は、保存する前にアプリで確認します。

キャプションは必須列にし、値がないときは空文字を保存します。

### 投稿日時の初期値

`created_at` は、行を挿入するときに現在日時を入れます。初期値には「日時を返す関数」を指定します。関数をその場で実行した時刻を初期値にすると、アプリ起動時の日時がすべての投稿に使われます。

### いいねの複合ユニーク

1人1回は、`user_id` と `post_id` の複合ユニークでデータベースにも保証します。アプリが先に存在確認をするだけだと、同じリクエストが重なったときに2件入ることがあります。

Peewee の複合インデックスには、列名ではなくモデルのフィールド名を指定します。フィールド名が `user` と `post` なら、インデックスの指定もその名前です。データベースにできる列は `user_id` と `post_id` です。

### パスワードと画像

`password_hash` へ書く前にハッシュ化します。データベースに平文を書きません。

画像のバイト列はテーブルに持ちません。許可した拡張子のファイルだけをフォルダへ保存し、保存時に付けたファイル名を `image_filename` に書きます。
